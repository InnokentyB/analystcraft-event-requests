# AnalystCraft: заявки на мероприятия
Отдельная полная эталонная версия приложения для воркшопа. React/Vite, браузерное хранилище и небольшой stateless HTTP-сервер. Это самостоятельный runtime-репозиторий; starter и существующий лендинг не изменялись.

## Запуск
Node.js 24, npm.

```sh
npm ci
npm run dev
```

Разработка: http://localhost:5173. Production:

```sh
npm run build
PORT=18080 npm start
```

Локальный просмотр: http://localhost:18080. По умолчанию сервер слушает 0.0.0.0:8080; PORT используется только для локального обхода занятого порта/платформ, которые его задают. GET /health возвращает 200 с `{"status":"ok"}`.

## Демонстрация за несколько минут
1. Роль «Сотрудник»: новая заявка, заполнить название, цель, аудиторию, дату, ответственного, бюджет; сохранить черновик и отправить.
2. Роль «Организатор»: согласовать. Открыть план подготовки.
3. Роль «Ответственный»: выполнить три обязательные задачи. Получить «Готово» и перезагрузить страницу.
4. Снять одну отметку: готовность исчезает. В карточке видна история решений и подготовки.
5. Отдельная ветка: организатор возвращает заявку с комментарием; сотрудник редактирует и повторно отправляет. Решения сохраняются в истории.

Кнопка «Добавить демо-заявки» добавляет три синтетические заявки один раз, не заменяет свои данные. Поиск учитывает название, аудиторию и ответственного; «Требуют действия» учитывает текущую учебную роль.

## Данные и ограничения
localStorage (`analystcraft.events.v1`), отдельно для браузера и origin. Переживает reload, но очистка браузера удаляет данные. На другом устройстве/домене данные независимы; общей базы и обмена между пользователями нет. Учебные роли ограничивают интерфейс, **не являются авторизацией или проверкой безопасности**. Вводите только синтетические данные. Нет внешних API, почты, оплаты, регистрации и ключей. История локальная, не является защищённым аудитом. Несколько одновременно изменяющих вкладок не поддерживают транзакции; используйте одну активную вкладку.

При отказе записи изменения не объявляются сохранёнными. При повреждении хранилища приложение блокирует запись и не затирает исходные данные. Для ручного восстановления сначала сохраните копию значения localStorage через инструменты браузера, затем исправьте данные/удалите только этот ключ. Автоматического удаления нет.

Допущения: бюджет в рублях, допустим ноль; даты в прошлом допустимы. У черновика обязательно название. Для отправки также обязательны цель, аудитория, дата, ответственный и бюджет. После отправки поля закрыты до возврата; после согласования три фиксированные обязательные задачи. Готовность вычисляется автоматически. Полный контракт и сценарии: docs/ACCEPTANCE.md и PRODUCT.md.

## Проверки

```sh
npx playwright install chromium
npm run test:e2e
E2E_BASE_URL=http://127.0.0.1:18080 npm run test:e2e
```

Desktop 1440×1000 и mobile 390×844, Chromium; правила согласования, возврат, повторная отправка, история, reload, демо, поиск, роли, ошибки хранения, безопасное отображение пользовательского текста, клавиатура и axe WCAG A/AA на всех трёх экранах. Формальные гарантии всей доступности/безопасности это не доказывает.

TDPD / Test-Driven Product Development — оригинальный метод Innokenty Bodrov. Сценарии и тесты созданы до реализации. Первый RED был заблокирован отсутствующим установленным браузером; реализация началась до исправления этого блока, что нарушило строгую последовательность RED gate. Поздний повтор на исходной пустой поверхности подтверждает отсутствие поведения, но не исправляет хронологию. Фактическая инженерная проверка GREEN и ручная приёмка независимы. UAT владельца ожидается; TDPD не объявлен завершённым. Факты прогонов: docs/VERIFICATION.md.
